> 上游文档：01-需求分析 V2.1 · 02-产品设计 · 03-渠道方案 · 04-免费版零成本方案（均已确认）
> 日期：2026-07-03
> 状态：初稿，待评审
> 约束回顾：SaaS 多租户 · 英语区首发 · **免费版 v0**（免费数据栈 / BYOK / 用户自有邮箱发送）
> · 小团队开发 · 基础设施月成本目标 <$50

## 1. 架构目标与决策基调

| 目标 | 由此推出的决策 |
|------|----------------|
| 免费版：变动成本≈0，固定成本极低 | 单 VPS 起步、避免托管云服务依赖、重活全部异步批处理 |
| 小团队快速迭代 | **模块化单体**（Modular Monolith），拒绝微服务；单语言全栈 |
| 序列引擎绝不能重发/漏停（信誉事故） | 状态机 + 幂等键 + 发送前三重校验，宁可不发不能错发 |
| 数据源/渠道会持续增减 | 适配器插件接口（03 文档 §5）为一等公民 |
| 未来付费版/扩容不推倒重来 | 租户隔离、计量、任务队列从 v0 就内建；扩容路径 = 加 worker，不改架构 |

**总基调：无聊的技术，谨慎的工程。** 创新点留给产品（AI 研判、个性化写信），
基础设施全部用最成熟的组合。

## 2. 技术选型（含理由与放弃项）

| 层 | 选型 | 理由 | 放弃的方案及原因 |
|----|------|------|------------------|
| 语言 | **TypeScript 全栈** | 前后端共享类型（线索/序列状态等复杂对象多）；Playwright 爬取生态好；招人容易 | Python（AI 生态好，但前后端两套语言，小团队负担）|
| 前端 | Next.js（App Router）+ Tailwind | 原型已是工作台形态，SSR 便于首屏与 SEO（营销页同仓库） | SPA+独立后端（多一层部署） |
| API | Next.js Route Handlers + tRPC | 单仓库单进程，类型端到端 | NestJS 独立服务（v0 过重，二期如需拆出 worker 服务再说） |
| 数据库 | **PostgreSQL 16** + Drizzle ORM | 唯一数据库：业务数据、队列、全文检索（pg_trgm）、JSONB 存研判档案 | MongoDB（无必要）；MySQL（缺 RLS/JSONB 优势） |
| 队列 | **BullMQ + Redis** | 成熟的延时任务/重试/并发控制，序列引擎的排程底座 | pg-boss（可行的备选，若想省 Redis 可切换，接口已抽象） |
| 爬取 | Playwright（自托管）+ 纯 HTTP 优先 | JS 站兜底渲染；HTTP 直取为主控成本 | 付费渲染服务（违背零成本） |
| 邮箱验证 | Reacher（开源，Docker 自托管，独立干净 IP 的 $5 VPS） | 04 文档决策 | 付费 Email Finder |
| 邮件收发 | Gmail API / Microsoft Graph（OAuth 2.0） | 用户自有邮箱发送；线程化回复检测 | SMTP/IMAP 通用兜底（二期，优先两大邮服覆盖 90% 用户） |
| LLM 接入 | 统一网关模块：BYOK（用户 Key）+ 平台 Key 双模式；模型分级路由 | 04 文档决策 | 自部署开源模型（运维成本反而高，后评估） |
| 部署 | 单 VPS + Docker Compose（app / worker / postgres / redis / caddy） | 月成本 $20–40；每日全量备份到对象存储 | K8s/托管 PaaS（成本与复杂度） |
| 可观测 | 结构化日志（pino）→ Loki 或纯文件 + Uptime 监控 | 够用 | 商业 APM |

**成本估算（v0）**：主 VPS ~$24/月 + 验证 VPS ~$5/月 + 域名/备份 ~$5/月 ≈ **$35/月**。

                        │              │ 写任务/读状态                                                  │
                        │              ▼                                                              │
                        │         PostgreSQL 16 ◀──────────┐            Redis (BullMQ)               │
                        │              ▲                    │                 ▲                        │
                        │              │                    │                 │                        │
                        │         Worker 进程（可多开，按队列分组消费）─────────┘                        │
                        │           ├─ discovery.*   线索发现/研判流水线（夜间批处理为主）                │
                        │           ├─ sequence.*    序列引擎 tick 与发送执行                            │

### 4.1 模块清单（与 02 文档 §4 对象模型对应）

| contact | 联系人/邮箱发现与验证 | contacts, email_candidates（置信度） |

| audit | 全链路事件（线索生命周期审计） | events（append-only） |

### 4.2 核心表关键设计点

```sql
-- 所有业务表带 tenant_id，启用 Postgres RLS（行级安全）双保险
companies(id, tenant_id, domain UNIQUE(tenant_id, domain), name, country, source, ...)
  -- 域名 = 租户内去重与撞单保护的唯一键（02 文档语义规则）
leads(id, tenant_id, company_id, campaign_id, owner_user_id, score, score_reason,
      status,  -- discovered|scored|ready|incomplete|in_sequence|replied|hot|nurturing|rejected|cooled|handed_off|suppressed|excluded
      ...)
research_facts(id, company_id, fact_text, source_url NOT NULL, fetched_at, expires_at)
  -- 每条事实必须有出处（反幻觉的数据层约束）；90 天过期驱动缓存刷新
email_candidates(id, contact_id, email, method, confidence, verify_status, verified_at)
sequence_states(id, tenant_id, contact_id, campaign_id, current_step, status,
      next_action_at, timezone, UNIQUE(contact_id, campaign_id))
send_jobs(id, sequence_state_id, step_no, idempotency_key UNIQUE, scheduled_at,
      status, message_id, ...)  -- 幂等键 = hash(sequence_state, step_no)：物理上杜绝重发
suppression_entries(tenant_id, email_or_domain, reason, source, created_at)
  -- 唯一索引 + 发送路径强制 JOIN 校验
events(id, tenant_id, entity_type, entity_id, event, payload JSONB, at)
  -- 线索全生命周期可回放（NFR 可观测）
```

## 5. 线索发现流水线（discovery）

### 5.1 流水线阶段（每阶段 = 一个 BullMQ 队列，失败独立重试）

```
icp.compile        ICP → 各适配器的查询计划（AI 生成搜索式/Maps 网格/CH 行业码）
  └▶ source.fetch    各 DataSourceAdapter 并行拉取 → company_candidates（原始）
      └▶ dedupe        域名归一化（去 www/协议/尾斜线）→ 租户内合并、全局撞单检查
          └▶ crawl        官网关键页抓取（HTTP 优先，Playwright 兜底；robots 遵从+限速）
              └▶ research     LLM 两级研判：cheap 初筛（是否目标行业/B2B）→ strong 精评
                              产出：score + score_reason + research_facts[]（每条带 source_url）
                  └▶ contacts     决策人抽取（About/Team 页+CH 董事）→ 邮箱模式生成
                      └▶ verify       Reacher SMTP 验证 → 置信度分级 → 高/中置信 → Lead 置 ready
```

### 5.2 工程要点

- **批处理窗口**：默认夜间执行（北京时间），早晨出结果——符合产品"昨夜战报"叙事，也错峰限流；
- **成本闸门**：strong 模型只精评 cheap 初筛 ≥60 分的候选；研判缓存按域名 90 天（跨租户共享
  **公开事实**，联系人数据绝不共享）；
- **适配器契约**（03 文档 §5）：每个源实现 `discover/enrich/findContacts`，注册即生效；
  适配器故障熔断（连续 N 次失败自动停用并告警），单源故障不影响流水线其余源；
- **免费额度调度**：各源的免费配额（PSE 100 次/天等）由 quota 模块集中记账，
  用完自动切换兜底源或顺延到次日——免费栈的核心运营逻辑。

## 6. 序列引擎（sequence）—— 全系统可靠性要求最高的模块

### 6.1 执行模型

```
每 5 分钟 tick：SELECT ... FROM sequence_states
  WHERE status='active' AND next_action_at <= now()  FOR UPDATE SKIP LOCKED
  → 逐条生成 send_job（幂等键防重）→ 入 BullMQ 延时队列（精确到投递窗口）
send_job 执行时【三重校验，任一失败即取消】：
  ① 压制名单检查（suppression_entries JOIN）
  ② 序列状态复查（是否已回复/已停止——处理 tick 与回复到达的竞态）
  ③ 发信身份健康与日限检查（mailbox 状态机 + 当日计数）
通过 → Gmail/Graph API 发送 → 写 message + 事件 → 推进 next_action_at 到下一步
```

### 6.2 四条不变量的实现（02 文档 §6.2 的技术承接）

| 不变量 | 实现机制 |
|--------|----------|
| 回复即全停 | 回复入库事务内：置 sequence_state=stopped + 取消该联系人所有 pending send_jobs（DB 状态位，job 执行时②复查兜底） |
| 绝不重发 | send_jobs.idempotency_key 唯一约束（数据库层物理保证，非应用层判断） |
| 全局频控 | 建 sequence_state 前检查：该联系人 30 天内无其他 active/completed 序列（唯一索引辅助） |
| 时区窗口 | 联系人时区（国家/城市推导）→ scheduled_at 计算为当地工作日 08:30–11:30 内随机点；窗口外只排队 |

### 6.3 发信身份健康状态机（mailbox）

`warming(21天爬坡: 5→20封/日) → healthy(≤20/日,免费版锁定) → throttled(退信>3%自动减半) → paused(投诉>0.1%熔断,人工恢复)`
— 计数器在 Redis（当日）+ Postgres（历史），状态变更写 events 并触发通知。

## 7. 邮件收发与回复处理（mailbox + triage）

- **发送**：Gmail API `messages.send` / Graph `sendMail`，自定义 `Message-ID`，
  线程化用 `In-Reply-To`/`References`；每封信注入退订链接（签名 token）与公司落款（合规）；
- **收件（v0 用轮询）**：每 3 分钟 `history.list`（Gmail）/ delta 查询（Graph）增量拉取
  ——避免 Gmail Push 所需的 GCP Pub/Sub 依赖，符合零成本；热线索时效目标 <5 分钟成立；
- **回复归属**：In-Reply-To/References 匹配 → 线程归属 → 触发序列停止（§6.2）；
- **分类**：cheap 模型分类（7 类，02 文档 P2）+ 置信度；低置信度 → 归入"待人工分拣"而非猜测
  （热线索漏报率趋零原则：宁可多推给人）；
- **退订处理**：退订链接点击（无需登录）与回信关键词（unsubscribe/remove me）双通道 → suppression；
- **OAuth Token**：refresh_token AES-GCM 加密落库，密钥在环境变量（v0）→ 二期迁 KMS；
  Token 失效 → 邮箱置 disconnected + 通知用户重连（序列自动暂停该身份）。

## 8. AI 编排层（ai-gateway）

```
调用方（research/写信/分类）→ ai-gateway.invoke(task, context)
  ├─ 路由：task → 模型档位（cheap: 初筛/分类/抽取；strong: 精评/写信/回复草拟）
  ├─ 密钥：租户 BYOK（AES-GCM 加密存储，调用时解密）→ 无则平台 Key + 配额扣减
  ├─ 上下文组装（RAG-lite）：BrandKit 可引用条目 + 该公司 research_facts（含出处）
  ├─ 产出校验（反幻觉闸门，写信任务强制）：
  │    · 事实性声明抽取 → 逐条匹配 BrandKit/facts 来源，无出处的具体数字/认证/日期 → 拒绝或改写
  │    · spam 词表与结构检查（字数/链接数/大写比例）→ 超标重生成
  ├─ 计量：llm_calls 记录 token/成本/租户 → quota 扣减
  └─ 提示词版本化：prompt_versions 表管理，灰度与回滚（回复率是提示词的验收指标）
```

BYOK 说明：v0 支持 Anthropic/OpenAI 两家 Key 自带；统一经 SDK 适配层调用，
供应商差异（工具调用/JSON 模式）封装在网关内。

## 9. 多租户与安全

- **隔离**：单库共享 schema + `tenant_id` + **Postgres RLS**（应用层 set_config 注入租户上下文，
  漏写 WHERE 也不会跨租户泄漏）；
- **加密**：OAuth token、BYOK 密钥 AES-256-GCM 应用层加密；备份加密；
- **权限**：Member 只见自有 Campaign/线索（owner_user_id）；Admin 租户全量——tRPC 中间件统一裁决；
- **GDPR**：联系人数据带来源与采集时间（FR-CNT-05）；删除请求 → 级联匿名化（events 保留脱敏轨迹）；
- **审计**：导出操作记录到 events；免费版导出限频。

## 10. 部署与运维（v0）

```
docker-compose：caddy(TLS) · app(Next.js) · worker(×2) · postgres · redis
备份：pg_dump 每日 → 对象存储（异地）· 保留 30 天
监控：healthcheck 端点 + 外部 Uptime 探测 + 队列积压告警（BullMQ metrics → 简单阈值）
发布：git push → 构建镜像 → compose 滚动重启（worker 先 drain 再停，序列任务不丢）
扩容路径（不改架构）：worker 拆到第二台 VPS → Postgres 独立 → 读写分离（远期）
```

## 12. 架构决策记录（ADR 摘要）

| # | 决策 | 状态 | 一句话理由 |
|---|------|------|-----------|
| ADR-1 | 模块化单体，不做微服务 | ✅ | 小团队+成本约束；模块边界已为拆分预留 |
| ADR-2 | TypeScript 全栈 | ✅ | 类型共享+爬取生态+单语言 |
| ADR-3 | Postgres 单库 + RLS 多租户 | ✅ | 免费版规模下最简可靠；RLS 兜底安全 |
| ADR-4 | BullMQ/Redis 做队列与排程 | ✅ | 序列引擎需要成熟的延时/重试语义（pg-boss 为备选） |
| ADR-5 | 收件用轮询不用 Push | ✅ | 免 GCP 依赖，3 分钟轮询满足 <5 分钟时效 |
| ADR-6 | 幂等键在数据库层防重发 | ✅ | 信誉事故不可依赖应用层逻辑 |
| ADR-7 | 反幻觉做成网关强制闸门而非提示词约定 | ✅ | 事实错误 = 品牌事故，必须结构化校验 |
| ADR-8 | v0 只接 Gmail/Outlook，不做通用 IMAP | ✅ | 覆盖 90% 目标用户，省一套协议栈 |

## 13. 开放问题（开发前需定）

1. BYOK 首发支持的模型供应商清单与推荐档位（建议：strong=claude-sonnet-5，cheap=claude-haiku-4-5，另支持 OpenAI Key）；
2. 联系人时区推导精度（国家级 vs 城市级）——影响投递窗口，建议 v0 国家级+城市修正表；
3. 爬取出口 IP 策略：主 VPS 直出 or 廉价代理轮换（涉及被目标站限流的概率，建议先直出+限速观察）；
4. 前端组件库：自研轻组件（原型风格已定）vs shadcn/ui 起步（建议后者提速）。
